# Инструкция по восстановлению TenderIntel (job-2)

Этот документ описывает, как развернуть проект заново на Amvera (или любом другом Node.js + PostgreSQL хостинге) после удаления текущего проекта. Все данные приложения (тендеры, пользователи, профиль компетенций) хранятся в PostgreSQL — при пересоздании окружения с нуля база будет пустой, но при первом старте сервер автоматически создаст таблицы и засеет демо-данные (см. ниже).

## 1. Что нужно перед началом

- Репозиторий GitHub с этим кодом (ветка `main`).
- PostgreSQL база данных (на Amvera можно подключить отдельный сервис БД, либо использовать внешний Postgres — например, Neon, Supabase, Amvera Postgres add-on).
- Строка подключения к БД вида `postgresql://user:password@host:port/dbname`.

## 2. Создание нового проекта на Amvera

1. Создать новый проект в личном кабинете Amvera, тип — **Node.js приложение**.
2. Подключить к проекту репозиторий GitHub (или загрузить код вручную).
3. Убедиться, что в корне репозитория есть файл `amvera.yaml` со следующим содержимым (он уже в репозитории, просто проверьте, что он не был случайно удалён):

```yaml
meta:
  environment: nodejs
  toolchain:
    name: npm
    version: "20"
build:
  additionalCommands: npm run build
  artifacts:
    "*": /
run:
  scriptName: dist/index.js
  persistenceMount: /data
  containerPort: 5000
```

Это означает:
- Используется Node.js 20 + npm.
- При деплое выполняется `npm install` (Amvera делает это автоматически), затем `npm run build`.
- Приложение запускается командой `node dist/index.js`.
- Контейнер слушает порт **5000**.
- `/data` — точка монтирования persistence-диска (если используется локальное хранилище; для текущей версии приложение хранит всё в PostgreSQL, поэтому этот том не критичен, но можно оставить как есть).

## 3. Переменные окружения

В настройках проекта Amvera (раздел "Переменные окружения" / Environment Variables) нужно задать:

| Переменная | Обязательна | Назначение | Пример |
|---|---|---|---|
| `DATABASE_URL` | Да (или `POSTGRES_URL`) | Строка подключения к PostgreSQL. Должна начинаться с `postgresql://` или `postgres://` | `postgresql://user:pass@host:5432/dbname` |
| `SESSION_SECRET` | Рекомендуется | Секрет для подписи cookie сессий. Если не задать — используется дефолтное значение из кода (`tender-ai-secret-key`), что небезопасно для продакшена | любая случайная длинная строка |
| `PORT` | Нет | Порт приложения. По умолчанию 5000, обычно Amvera сама подставляет нужный | `5000` |
| `NODE_ENV` | Нет | Если не `development` — приложение считает себя в продакшен-режиме (раздаёт статику из `dist`, включает `secure` cookies) | `production` |

Без `DATABASE_URL`/`POSTGRES_URL` сервер при старте упадёт с ошибкой:
`No valid DATABASE_URL or POSTGRES_URL found (must start with postgresql:// or postgres://)`
(см. `server/db.ts`).

## 4. Важно: настройка cookie за обратным прокси

Amvera (как и большинство PaaS) терминирует SSL на стороне nginx/прокси перед контейнером приложения. Без специальной настройки Express считает соединение нешифрованным и не отправляет `secure` cookies — из-за этого пользователи получают ошибку **"Unauthorized"** даже после успешного логина.

В коде уже есть исправление в `server/index.ts`:
```ts
app.set("trust proxy", 1);
```
Эта строка должна стоять **до** настройки `express-session` middleware. Если вы переносите код в новый проект руками (не просто пуш в Git), убедитесь, что эта строка не потерялась — это критично для работы авторизации в продакшене за реверс-прокси.

## 5. Сборка и запуск

Скрипты в `package.json`:

```json
"scripts": {
  "dev": "tsx server/index.ts",
  "build": "tsx script/build.ts",
  "migrate": "tsx script/migrate.ts",
  "seed": "tsx server/seed.ts",
  "start": "node dist/index.js"
}
```

- **Локальная разработка:** `npm install && npm run dev` (нужен `.env` с `DATABASE_URL`).
- **Продакшен-сборка:** `npm run build` — собирает клиент (Vite) и бэкенд (esbuild → `dist/index.js`, ESM с `packages: "external"` и `createRequire`-баннером для CJS-совместимости).
- **Запуск собранного билда:** `npm start` (= `node dist/index.js`). Именно эту команду использует Amvera через `scriptName: dist/index.js`.

Если разворачиваете через `Dockerfile` (есть в репозитории) вместо Amvera-сборки:
```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build
EXPOSE 5000
CMD ["npm", "start"]
```
Подходит для любого Docker-совместимого хостинга (Amvera, Render, Railway, VPS и т.д.).

## 6. Автоматические миграции и сеед-данные

При каждом старте сервера (`server/index.ts`, в самом конце файла) выполняются:

```ts
await runMigrations();
await runSeed();
```

**`runMigrations()`** — создаёт (если их ещё нет) таблицы:
- `users`
- `tenders`
- `saved_tenders`
- `competency_profiles`
- `tender_competencies`

Используются `CREATE TABLE IF NOT EXISTS`, поэтому повторные запуски безопасны и идемпотентны. Никакого отдельного шага "накатить миграции" не требуется — достаточно один раз запустить приложение с правильным `DATABASE_URL`.

**`runSeed()`** — при первом старте на чистой базе создаёт:
- Демо-пользователя: **логин `demo`, пароль `demo123`** (email `demo@tenderai.ru`, план `pro`).
- Демо-профиль компетенций (~25 технологий по направлениям: Backend, Frontend, Базы данных, DevOps, AI/ML, Интеграции, Мобильная разработка, Тестирование, Аналитика) — этот профиль перезаписывается актуальными данными при каждом старте (`UPDATE`, если профиль уже существует).
- 10 демо-тендеров с разным уровнем совпадения (от 95% до 28%) и привязанными к ним требованиями по компетенциям — добавляются только если их ещё нет в базе (проверка по `url`).

То есть **после восстановления на новой базе всё развернётся само** при первом старте контейнера — никаких ручных SQL-команд выполнять не нужно.

## 7. Проверка после деплоя

1. Открыть домен проекта — должна загрузиться страница логина.
2. Войти как `demo` / `demo123`.
3. Проверить, что список тендеров не пуст (10 демо-тендеров).
4. Открыть любой тендер — должна посчитаться и отобразиться "Наша оценка" с радар-диаграммой.
5. Открыть раздел "Наш профиль" (`/competencies`) — должны быть проставлены демо-компетенции.
6. Если логин происходит, но дальше выдаёт "Unauthorized" — см. раздел 4 (trust proxy).
7. Если приложение не стартует (502/503) — проверить в логах Amvera, что `DATABASE_URL` задан и БД доступна из контейнера.
